# Review of ThitsaX/pm4ml-deployment @ 8a2b3d0 (2026-03-11)

Reviewed on 2026-11-18 against the PM4ML charts and images published upstream,
and against the Mojaloop switch's DFSP onboarding flow.

## Verdict

The repo is **not ready to onboard a DFSP onto a Mojaloop switch as it stands.**
It is a minimal Helm install of the SDK scheme adapter and a simulator core
connector, with management-api and Vault removed. Four defects stop it from
transacting. Onboarding is fully manual, so certificates and JWS keys are
exchanged by hand outside MCM. The chart and images are one minor version behind
upstream and well behind what our sandbox was validated with.

## Defects that stop it from working

| # | Problem | Effect | Fixed here |
|---|---|---|---|
| 1 | `INBOUND_MUTUAL_TLS_ENABLED: true`, with no `IN_CA_CERT_PATH` / `IN_SERVER_CERT_PATH` / `IN_SERVER_KEY_PATH` set | The inbound HTTPS server starts without a certificate. Every hub callback fails at the TLS handshake (read from the code: `InboundServer._createServer`) | IN_* paths set, certificates from Secret `pm4ml-tls` |
| 2 | The Istio VirtualService terminates TLS at the gateway and routes HTTP to port 4000, which speaks HTTPS | Callbacks cannot reach the SDK, even after fixing 1. The hub's mTLS also ends at the DFSP gateway rather than at the SDK | The chart's callback Service, Istio Gateway or ingress-nginx options, all with TLS passthrough (`callback.*`) |
| 3 | The outbound client certificate is `servercert.pem`, issued by the DFSP's own CA (`pm4ml-conn-wallet3 Root CA`) | Our edge only accepts client certificates signed by the hub CA, so outbound mTLS is refused | Separate `client.pem` (hub-signed) and `server.pem` (DFSP CA). `create-secrets.sh` checks the chain |
| 4 | `JWS_SIGN: false`, `VALIDATE_INBOUND_JWS: false` | Peers that validate JWS (every PM4ML and SDK DFSP on our sandbox) reject its messages with `3105`. It also accepts forged messages | JWS on, with the key paths the chart actually mounts (`/jwsSigningKey.key`, `/jwsVerificationKeys`). The chart's defaults point elsewhere |

## Security findings

| Finding | Action |
|---|---|
| **A real private key is committed** (`networking/pm4ml-mtls.yaml`): the server key for `conn-wallet3.dev2.thitsa-connect.com`, public on GitHub. The certificate expired 2026-07-14, but the key must be treated as compromised | Removed here. **Tell ThitsaX**: revoke it, make sure the key is not reused, and purge it from git history |
| `ILP_SECRET` is the chart's default (`Quaixohyae…`), the same for every install | A known ILP secret lets anyone who sees a quote's ILP packet compute its fulfilment. Now per-install, random, from a Secret |
| Redis password `passw0rd` in values and in the HAProxy health check | Removed. The chart's Valkey runs with a password, the Redis URL lives in Secret `<release>-runtime` (`cache-url`), and NetworkPolicies cover the Redis and HAProxy pods |
| The outbound API (4001) and the core connector (3003/3004) are published through the public gateway (`sdk-vs`, `core-connector-*-vs`) | Neither authenticates its callers. Anyone who reaches them can start a transfer. They are no longer published |
| The chart's `testIngress` was left enabled (host `pm4ml.test`, routes to the outbound API) | Disabled |
| `ENABLE_TEST_FEATURES: true` (chart default) | Kept on, to match Compose; the test API (port 4002) is never published |

Upstream activity has moved from the Helm chart (last real change 2025-12) to
`pm4ml/pm4ml-docker-compose`, which tracks newer images. The Helm chart still
pins management-api 6.8.0, and its bundled Bitnami Redis image
(`docker.io/bitnami/redis:7.0.8-debian-11-r0`) is no longer published there.
Compose now uses `bitnamilegacy/`. Expect to override image tags in the Helm
chart rather than rely on its defaults.

## Smaller issues

- The README refers to `networking/ingress.yaml`. The file was `pm4ml-ingress.yaml`.
- mTLS was mounted with `kubectl apply` of a partial Deployment after install.
  Helm does not track it, so the mount is easy to lose or to diverge from.
  This chart renders the mounts itself.
- `API_TYPE` and `ILP_VERSION` were not set. They must match the hub
  (`iso20022` uses ILP v4). A mismatch fails every call with
  `3101 Invalid accept header`.
- No `Hub` JWS key. A DFSP acting as payee rejects the hub's commit
  notification and reports a timeout for a transfer that settled.

## Status

The validation status is in the README. The repo's defaults now follow
JengaCore/pm4ml-docker-compose (MCM mode with Vault), not ThitsaX's static mode,
which remains available as `values-static.yaml`.
